Lines the parser does not recognise are skipped, as the CLI does. Duration and per-band time are computed between event timestamps, so a log with few events gives coarse numbers.

How it works

A streaming parser feeds a stateful tracker. The tracker always knows which cells are up.

1

Parse as a stream

Compiled regexes turn each log line into a typed entry: cell add and deactivate, CA state change, measurement report, throughput, RLF and re-establishment. Lines are read one at a time.

2

Track CA state

The classifier keeps the primary cell and secondary cells as events arrive, so every event carries the component carrier count at that moment.

3

Report three ways

A terminal view, JSON and CSV for pipelines, and a CA efficiency report with time per carrier count and per band combination.

Run it on your own logs

Python 3.11 or later. Standard library only.

pip install git+https://github.com/gerardrecinto/nr-ca-analyzer

nr-ca-analyzer analyze fixtures/sample_events.log
nr-ca-analyzer analyze fixtures/sample_rlf.log --format json
nr-ca-analyzer stats fixtures/sample_events.log
nr-ca-analyzer analyze log.txt --band n41,n78
nr-ca-analyzer analyze log.txt --filter-kind SCEL_ADD,RLF
nr-ca-analyzer analyze log.txt --since 09:15:30 --until 09:16:45

The analyzer filters by band, event kind and time window, and writes CSV for spreadsheets.

What this does not do
  • It reads a text format the repo defines for simulated diagnostic logs. It does not decode a vendor's binary modem trace.
  • The sample logs are lab-style examples, so the numbers describe those examples, not any real network.
  • It reports what happened in a log. It does not tune a network or diagnose a root cause for you.
